# Lab 5. Подкасты: JWT access/refresh и управление сессиями (вариант 12)

Лабораторная работа по дисциплине «Разработка безопасного программного обеспечения».
REST API системы публикации подкастов из Лабы 4 (Spring Security: HTTP Basic, CSRF-защита, регистрация, роли и
правила доступа) дополнен выдачей пар JWT (access и refresh, подпись HS256), обновлением пары и серверным учётом
refresh-сессий в БД.

## Стек

- Java 21, Spring Boot 4.1.1 (Spring MVC, Spring Data JPA / Hibernate, Spring Security), Bean Validation, Lombok
- JWT: `spring-security-oauth2-jose` (Nimbus JOSE + JWT), алгоритм HS256
- PostgreSQL 16 (в Docker), драйвер `org.postgresql:postgresql`
- Maven (`mvnw`)

## Что добавлено по сравнению с Лабой 4

| Требование | Реализация |
|---|---|
| Сущность сессии | `UserSession` (таблица `user_sessions`) и `enum SessionStatus` (`ACTIVE`, `USED`, `REVOKED`): одна запись - одна пара токенов |
| Генерация и проверка JWT | `JwtService`: отдельные операции для access и refresh, HS256, новый `jti` для каждой выдачи, время жизни из настроек |
| Выдача и обновление пары | `TokenPairService`: `issue` и `refresh`, поиск, проверка статуса, изменение старой записи и сохранение новой в одной транзакции |
| Access-фильтр | `JwtAuthenticationFilter`: принимает только access-токен в заголовке `Authorization: Bearer` |
| Контроллер | `POST /auth/login` (200), `POST /auth/register` (201), `POST /auth/refresh` (200), в ответе пара токенов |
| Обновление refresh | старая запись `USED`, новая `ACTIVE`; повторный refresh отзывает запись (`REVOKED`) и получает `401` |

Остальное (HTTP Basic, CSRF, роли, права, бизнес-операции) осталось как в Лабе 4. Далее описано то, что было в Лабе 4.

## Что было добавлено в Лабе 4 по сравнению с Лабой 3

| Требование | Реализация |
|---|---|
| HTTP Basic Auth | `SecurityConfig`: `httpBasic`, сессии отключены (`STATELESS`), каждый запрос проверяется заново |
| CSRF для изменяющих запросов | включена для `POST`, `PATCH`, `DELETE`; токен хранится в cookie `XSRF-TOKEN` (double submit cookie) и передаётся в заголовке `X-XSRF-TOKEN` |
| Получение CSRF-токена | `GET /api/auth/csrf` возвращает `{headerName, parameterName, token}` и выставляет cookie |
| Учётные записи в БД | таблица `users` дополнена полями `password_hash`, `role`, `status`, `failed_login_attempts`, `locked_until` |
| Безопасное хранение паролей | `PasswordEncoder` (`BCryptPasswordEncoder`), в БД хранится только хеш |
| Регистрация | `POST /auth/register`: проверка надёжности пароля и уникальности логина и e-mail |
| Учёт состояния пользователя | `ACTIVE` / `BLOCKED` и временная блокировка после серии неудачных входов |
| Нет самостоятельного повышения привилегий | регистрация всегда создаёт `USER`, поля `role` и `status` из тела запроса игнорируются |
| Роли и права | роли `USER`, `MODERATOR`, `ADMIN`, у каждой свой набор прав (authorities) |
| Доступ через `SecurityFilterChain` и `@PreAuthorize` | грубые правила по методу, пути и праву в цепочке фильтров, точные (владелец, контекст) через `@PreAuthorize` |
| Различение ошибок | `401` - не аутентифицирован, `403` - не хватает прав или нет CSRF-токена, `409` - нарушено бизнес-ограничение |
| Ошибки без чувствительных данных | единый формат без стек-трейсов, причина отказа во входе не раскрывается |

## Аутентификация

- Эндпоинты API по-прежнему принимают HTTP Basic: заголовок `Authorization: Basic base64(логин:пароль)` в каждом
  запросе. Дополнительно принимается access-токен JWT в заголовке `Authorization: Bearer <accessToken>` (см. раздел
  «JWT-токены и refresh-сессии»).
- `AppUserDetailsService` загружает пользователя из БД (логин без учёта регистра), `DaoAuthenticationProvider`
  сверяет пароль с BCrypt-хешем.
- Любая причина отказа во входе (неверный пароль, неизвестный логин, заблокированный пользователь, временная блокировка)
  даёт один и тот же ответ `401` с одним сообщением, чтобы по ответу нельзя было перебирать логины и узнавать состояние
  учётной записи. Причина пишется только в лог сервера.
- Basic передаёт пароль открытым текстом (в base64), поэтому вне учебной среды сервис нужно запускать только по HTTPS.

### Регистрация и пароли

`POST /auth/register` с телом `{"username", "email", "password"}`.

- логин: 3-50 символов, буквы, цифры, `_`, `.`, `-`; логин и e-mail уникальны без учёта регистра (`409`, если заняты);
- пароль: от 10 символов, не больше 72 байт (ограничение BCrypt), строчная и заглавная буквы, цифра, спецсимвол,
  не содержит логин и не входит в список распространённых паролей (`400`, в ответе перечислены нарушенные правила,
  сам пароль не возвращается и не логируется);
- созданный пользователь всегда `USER` и `ACTIVE`; ответ не содержит ни пароля, ни хеша.

### Состояния пользователя

| Состояние | Как возникает | Что происходит |
|---|---|---|
| `ACTIVE` | регистрация, разблокировка | вход разрешён |
| `BLOCKED` | администратор вызывает `POST /api/users/{id}/block` | вход невозможен, пока администратор не вызовет `unblock` |
| временная блокировка | 5 неудачных входов подряд (`app.security.max-failed-attempts`) | вход невозможен 15 минут (`app.security.lock-duration`), затем снимается сама; администратор может снять раньше |

Успешный вход сбрасывает счётчик неудачных попыток. Подсчёт ведёт слушатель событий аутентификации
(`AuthenticationEvents` + `LoginAttemptService`).

## JWT-токены и refresh-сессии

### Контракт

| Endpoint | Тело запроса | Успешный ответ |
|---|---|---|
| `POST /auth/login` | `{"username", "password", "deviceId"?}` | `200`, пара токенов |
| `POST /auth/register` | `{"username", "email", "password", "deviceId"?}` | `201`, пара токенов |
| `POST /auth/refresh` | `{"refreshToken"}` | `200`, новая пара токенов |

Эти три endpoint находятся по путям `/auth/...`; остальные endpoint API (`/api/auth/csrf`, `/api/auth/me`, `/api/users`, `/api/podcasts` и так далее) остались по путям из Лабы 4.

Успешный ответ каждого из трёх endpoint: `{"accessToken": "<JWT>", "refreshToken": "<JWT>"}`. Access передаётся в
заголовке `Authorization: Bearer`, refresh - в теле JSON. `/auth/refresh` не требует access-токена и пароля;
`deviceId` (до 100 символов) - необязательная метка клиента.

Ошибки (тело без новой пары токенов):

| Ситуация | Код |
|---|---|
| неверные учётные данные при входе (в том числе заблокированный пользователь) | `401` |
| отсутствует или пустое обязательное поле | `400` |
| неверный, просроченный или не того типа refresh | `401` |
| неизвестная, использованная или отозванная refresh-сессия | `401` |
| повторная регистрация существующей учётной записи | `409` |

### Токены

Оба токена - JWT с подписью HS256 (`JwtService`). Ключ берётся из `JWT_SECRET` (файл `.env`, не короче 32 байт),
время жизни - из `app.jwt.access-ttl` (15 минут) и `app.jwt.refresh-ttl` (7 дней).

| Claim | Значение |
|---|---|
| `sub` | логин владельца |
| `jti` | новый UUID для каждой выдачи |
| `iat`, `exp` | время выдачи и истечения (секундная точность) |
| `type` | `access` или `refresh` |

Проверка каждого токена включает подпись, срок действия (без допуска на расхождение часов), наличие обязательных
claims и значение `type`. Access-фильтр принимает только `access`, обработчик обновления - только `refresh`.
Некорректный Bearer-токен в обычном запросе даёт `401`; на `login`, `register` и `refresh` заголовок `Authorization`
игнорируется.

### Сессии (`user_sessions`)

Одна запись соответствует одной паре токенов: `id` (UUID), `username`, `device_id`, `access_token`, `refresh_token`
(уникален), `access_token_expiry`, `refresh_token_expiry`, `status`. Время истечения в записи равно `exp`
соответствующего токена. Таблица создаётся в `db/init/02-schema.sql`, у роли приложения есть `SELECT`, `INSERT`,
`UPDATE`, `DELETE`.

| Статус | Значение |
|---|---|
| `ACTIVE` | refresh ещё не использован и не отозван |
| `USED` | refresh успешно применён для обновления |
| `REVOKED` | refresh отозван |

### Выдача и обновление пары (`TokenPairService`)

Выдача пары: пользователь получен после входа или регистрации, созданы access и refresh, сессия сохранена
со статусом `ACTIVE`, пара возвращается только после успешного сохранения. Регистрация и выдача пары выполняются
в одной транзакции: если сессию сохранить не удалось, пользователь не создаётся.

Обновление пары выполняется в одной транзакции (`@Transactional`):

1. refresh проверяется как JWT, `type` должен быть `refresh`;
2. по значению токена находится сессия (запись блокируется на время операции, `SELECT ... FOR UPDATE`);
3. проверяется, что пользователь существует и не заблокирован, `sub` совпадает с владельцем записи,
   статус `ACTIVE`, `refreshTokenExpiry > now`;
4. старая сессия переводится в `USED`;
5. создаются новая пара и новая сессия `ACTIVE` с тем же пользователем и `deviceId`;
6. изменения фиксируются одной транзакцией, возвращается новая пара.

Если новая пара не сохранена, изменение старой сессии откатывается. При двух одновременных запросах с одним refresh
обмен проходит только у одного: второй дожидается блокировки, видит статус `USED` и получает отказ.

При повторном предъявлении ещё не истёкшего refresh со статусом `USED` запись переводится в `REVOKED`, возвращается
`401` без новой пары, а изменение `REVOKED` сохраняется несмотря на отказ (транзакция не откатывается для этого
исключения). Для уже отозванной сессии также возвращается `401`. Отзыв всей цепочки обновлений и немедленный отзыв
access не выполняются.

### CSRF и Bearer

CSRF-защита из Лабы 4 включена для `POST`, `PATCH`, `DELETE`. Токен не требуется только там, где его нечем подделать:
`POST /auth/login`, `POST /auth/refresh` (учётные данные и refresh лежат в теле запроса) и запросы с заголовком
`Authorization: Bearer` (токен не подставляется браузером автоматически). Регистрация и запросы с HTTP Basic требуют
CSRF-токен, как и раньше.

## CSRF

Токен выдаёт `GET /api/auth/csrf`. Дальше клиент отправляет его в заголовке `X-XSRF-TOKEN` вместе с cookie `XSRF-TOKEN`
во всех запросах `POST`, `PATCH`, `DELETE`, включая регистрацию. Запрос без токена или с неверным токеном получает
`403` с кодом `CSRF_INVALID` ещё до проверки учётных данных. `GET` токена не требует.

```bash
curl -c jar.txt -b jar.txt http://localhost:8080/api/auth/csrf
curl -b jar.txt -u 'ivan:Ivan#Pass2026' -X POST http://localhost:8080/api/episodes/5/publish-now \
     -H 'X-XSRF-TOKEN: <token из ответа>'
```

## Роли и права

| Роль | Права (authorities) | Что может |
|---|---|---|
| `USER` | `CONTENT_WRITE` | управлять своими подкастами, эпизодами, файлами и слотами; видеть свой профиль и чужой опубликованный контент |
| `MODERATOR` | `CONTENT_WRITE`, `PODCAST_MODERATE` | то же для своего контента; кроме того видеть весь контент, архивировать и восстанавливать любой подкаст, отменять любой слот |
| `ADMIN` | `CONTENT_WRITE`, `PODCAST_MODERATE`, `USER_MANAGE` | всё перечисленное, управление любым контентом, список и профили пользователей, блокировка, смена ролей, удаление |

Роль и права попадают в `GrantedAuthority`: `ROLE_USER` и т.д. плюс отдельные права.

### Правила доступа

Доступ проверяется на двух уровнях. `SecurityFilterChain` отсекает запрос по методу, пути и праву
(`hasAuthority`), всё, что не описано явно, закрыто (`denyAll`). `@PreAuthorize` на методах контроллеров
уточняет правило по контексту операции через бин `AccessPolicy` (имя `access`): кому принадлежит объект и в каком он
состоянии.

| Операция | Кто может |
|---|---|
| `GET /api/auth/csrf`, `POST /auth/register` | все |
| `GET /api/auth/me` | любой вошедший |
| `GET /api/users` | `ADMIN` |
| `GET`, `PATCH /api/users/{id}` | сам пользователь или `ADMIN` |
| `POST /api/users/{id}/block`, `/unblock`, `/role`, `DELETE /api/users/{id}` | `ADMIN` |
| `GET` подкастов, эпизодов, файлов | см. «Видимость» ниже |
| создать подкаст | любой вошедший; автор - он сам, указать другого автора может только `ADMIN` |
| изменить, удалить подкаст; создать, изменить, удалить эпизод и файл; запланировать, изменить, удалить и опубликовать слот; `publish-now`, `make-main` | автор подкаста или `ADMIN` |
| сменить автора подкаста (`PATCH` с `authorId`) | `ADMIN` |
| `archive`, `restore` подкаста, `cancel` слота | автор подкаста, `MODERATOR` или `ADMIN` |

Контекст операции влияет и на результат, а не только на роль:

- **Видимость.** Чужие подкасты видны, пока они `ACTIVE`; архивные видны только автору и персоналу
  (`MODERATOR`, `ADMIN`). Эпизод и его файлы видны другим пользователям только после публикации и пока подкаст
  активен, черновики и запланированные эпизоды видны автору и персоналу. Слоты публикации видны автору и персоналу.
  Скрытый объект для остальных выглядит как несуществующий: при чтении `404`, а при изменении
  обычный пользователь получает `403` и для скрытого, и для несуществующего id, поэтому по ответу нельзя узнать,
  что объект есть. В списках скрытые объекты отсутствуют.
- **Состояние.** Правила Лабы 3 действуют поверх прав: нельзя публиковать эпизод без основного файла, менять файлы
  опубликованного эпизода, добавлять эпизоды в архивный подкаст и т.д. (`409`).
- **Администратор** не может заблокировать, удалить или сменить роль самому себе (`409`), поэтому в системе всегда
  остаётся хотя бы один администратор.

## Обработка ошибок

Формат ответа: `{"status": 403, "code": "FORBIDDEN", "message": "Access denied"}`.

| Код | `code` | Когда |
|---|---|---|
| `400` | `VALIDATION_ERROR`, `BAD_REQUEST`, `MALFORMED_REQUEST` | неверные данные, слабый пароль, нечитаемое тело |
| `401` | `UNAUTHENTICATED` | нет учётных данных, они неверны, пользователь заблокирован |
| `403` | `FORBIDDEN`, `CSRF_INVALID` | недостаточно прав, нет или неверен CSRF-токен |
| `404` | `NOT_FOUND` | объекта нет или он скрыт от этого пользователя |
| `405`, `415` | `METHOD_NOT_ALLOWED`, `UNSUPPORTED_MEDIA_TYPE` | неподходящий метод или тип содержимого |
| `409` | `BUSINESS_RULE_VIOLATION`, `DATA_CONFLICT`, `RESOURCE_BUSY` | нарушено бизнес-ограничение, ограничение БД, конфликт блокировок |
| `500` | `INTERNAL_ERROR` | внутренняя ошибка без подробностей (детали пишутся только в лог) |

Ответы `401` и `403` формируют `ApiAuthenticationEntryPoint` и `ApiAccessDeniedHandler`, остальные -
`GlobalExceptionHandler`. Тексты ошибок не содержат паролей, хешей, SQL и стек-трейсов.

## Известные ограничения

- Access-токен нельзя отозвать немедленно: он действует до `exp` (15 минут), хотя после блокировки пользователя
  Bearer-запросы отклоняются, так как состояние пользователя проверяется при каждом запросе.
- Переименование пользователя (`PATCH /api/users/{id}`) делает его refresh-сессии непригодными (владелец записи
  ищется по логину), потребуется новый вход.
- Просроченные сессии из `user_sessions` не удаляются автоматически.

- Временная блокировка по неверным паролям считается по логину, поэтому любой может на 15 минут заблокировать чужую
  учётную запись, перебрав неверные пароли. В учебном проекте это принятый компромисс; в боевой системе добавили бы
  ограничение по IP и задержку.
- Список распространённых паролей в `PasswordPolicy` короткий и нужен для демонстрации; в боевой системе подключают
  большой словарь утёкших паролей.
- Тестовые пароли из `db/init/03-seed.sql` предназначены только для разработки.

## Коллекция запросов

`postman/lab5.postman_collection.json` (Postman: *Import* → выбрать файл). Запускать целиком через Collection Runner,
папки по порядку, на свежей БД.

0. **Подготовка**: получение CSRF-токена (заголовок `X-XSRF-TOKEN` добавляет скрипт коллекции, cookie подставляет Postman).
1. **Регистрация и аутентификация**: регистрация двух пользователей, дубликат (`409`), слабый пароль (`400`),
   попытка стать администратором через тело запроса, вход, неверный пароль, анонимный запрос, заблокированный
   пользователь (`401`), запрос без токена и с поддельным токеном (`403`).
2. **Сценарий владельца**: создание подкаста, эпизода и файла, отказ публикации без основного файла, назначение
   основного файла, планирование, ранняя публикация слота (`409`), отмена, публикация сейчас, заморозка файлов.
3. **Права разных пользователей**: другой пользователь, модератор и администратор выполняют те же операции с
   чужими данными (успех и отказы `403`, `404`, `409`), архивирование и восстановление подкаста.
4. **Администрирование**: блокировка и разблокировка, смена ролей, запреты на действия над самим собой.
5. **JWT: access/refresh и управление сессиями**: регистрация и вход с получением пары, доступ с access, обмен
   refresh, повторный старый refresh (`401`), подмена типа токена, поддельные токены, пустые поля, неверный пароль;
   запрос для проверки записей в БД приведён в описании папки.
6. **Изменение и удаление владельцем, очистка**: `PATCH`, `DELETE`, каскадное удаление пользователя.
